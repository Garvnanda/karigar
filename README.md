# Karigar

**An AI artisan for the jeweller's counter.** A jeweller types a request the way they speak it, in Hinglish or English:

> Purani 8.4g 22K chain exchange karni hai, uske badle 22K ladies ring chahiye, size 12, chhota floral design

About 20 seconds later, on a laptop CPU, Karigar replies with three castable designs, each solved to the gold the customer brought in. Every design comes with its finished weight ± tolerance, a rendered photo, a 3D model, a shrinkage-scaled STL, a workshop job card and a quote where every line names its source. If something can't be made, Karigar says which rule blocks it and offers two options that can.

The LLM never produces a number. Weights come from the mesh, prices from the rate card and today's gold rate, and dimensions from the size chart. The LLM is optional, and the whole demo runs offline.

## What it does

| | |
|---|---|
| **Understands the counter** | Hinglish/English (replies in the same language), Indian ring sizes 1–30, bangle 2-N sizes, chain lengths, old-gold exchanges, budgets. Asks at most 3 questions, and only for blocking fields. Never guesses a size or a purity |
| **19 original designs** | Rings (floral cluster, three-stone, halo, butterfly), pendants (heart halo, paisley, temple lotus), rope and curb chains, a 10 g lotus coin, bangles (temple kada, twisted rope, leaf vine), earrings (jhumka, chandbali, floral stud, bali), a nose pin and a convertible nose/ear stud. Every one is parametric, weight-solvable and orderable |
| **Solves to the gram** | Scales each design until mesh volume × alloy density hits the target (within 0.1 g or 2%), with stone seats cut out. Budget mode solves stone size and gold together |
| **Checks it can be cast** | Ray-cast thickness measured on the mesh: ring shank, prongs, walls, chain wire, soft 22K claws on big stones. Gives pass / warn / fail with a location, and retries once with a relaxed design |
| **Quotes honestly** | Gold at today's rate (MCX + ₹5,000 per 10 g, timestamped, refused if older than 24 h), 3.5% making, stones, ₹75 hallmarking per article, GST 3% + 5% on making, and the old-gold credit. Each line says where its number came from and whether it is assumed |
| **Edits** | "Middle one, but make the flower slightly bigger" changes only the flower and re-solves the band so the gold stays the same. "1 g halka karo" reports the weight and ₹ difference |
| **Learns the workshop** | Record actual cast weights, and the workshop's loss % and ± tolerance are learned from them |
| **Lives in Nonilion** | Two agents, **Sakhi** (counter) and **Karigar** (workshop), imported as OpenAI-compatible endpoints. A thin service on Render queues jobs, and a Blender worker on the laptop polls it. No tunnel is needed |
| **Owner console** | A web page with orders, a rotatable 3D model of every design, quote lines, a catalogue and a "Try it" chat for when Nonilion is down |

## How the weight solving works

Old-gold exchange, worked through (18.4 g of 22K):

1. **Fine gold**: 18.4 g × 0.916 purity × (1 − 2% deduction) = 16.52 g of fine gold.
2. **Finished weight** at the new karat: 16.52 ÷ 0.916 = 18.03 g.
3. **Casting weight**: 18.03 ÷ (1 − workshop loss) = 18.59 g at the default 3%. The loss is learned per workshop by `calibrate`.
4. **Solve**: each design has one monotone scale knob, and the ring size never scales. The solver probes the real mesh (stone seats cut) × density from `data/casting.json` and converges in 4–6 builds, all cached by spec hash.
5. **Cast or refuse**: casting rules bound the scale, and mesh checks run at the solved scale. Outside the bounds, the reply names the binding rule, the best achievable weight and two alternatives. Example: "22K, under 1.2 g, 1 ct stone" is refused with the lightest weight that can actually be cast.

**Proof that the mesh weight is right.** Mesh volume vs closed-form volume (Pappus for bands, ellipsoid for the disc pendant) is within 0.5% on every shape. The table is generated by a test: [docs/weight-proof.md](docs/weight-proof.md). The claim to make is "within ± tolerance after finishing", not the solver's precision. Casting variance is real, and calibration is what closes it.

## Quick start (WSL, Python 3.13)

```bash
uv venv --python 3.13 venv && VIRTUAL_ENV=venv uv pip install -r requirements.txt
./venv/bin/python run.py rates refresh          # today's gold rate (orders refuse without one < 24 h old)
./venv/bin/python run.py order "Nani ka purana 18.4g 22K kangan hai, naya 22K beaded kada banana hai, size 2-6" --quality draft
./venv/bin/python run.py order "18K 1 ct diamond ring under 10k, size 12"     # impossible: rule + options
./venv/bin/python run.py order "kuch sundar sa bana do"                        # unclear: asks, in Hinglish
./venv/bin/python run.py edit <order_id> "Middle one, but make the flower slightly bigger" --quality draft
./venv/bin/python run.py calibrate --workshop dariba-01 --designed 18.58 --actual 17.95
```

Each order writes `out/ORD-…/v1..v3/`: `render_hero.png`, `casting.stl` (gold only, +1% shrinkage), `model.glb`, `job_card.md` / `.json` and `quote.json`. Every order and version is also saved in `data/orders.sqlite3`.

**Service + worker + console locally:**
```bash
export KARIGAR_API_KEY=… KARIGAR_WORKER_TOKEN=… KARIGAR_OWNER_TOKEN=… KARIGAR_SERVICE_URL=http://127.0.0.1:8080
./venv/bin/python run.py serve &      # stdlib only: OpenAI-compatible /v1, /sakhi/v1, /karigar/v1, JSON /api, /console/
./venv/bin/python run.py worker       # bpy + optional claude CLI: claims jobs, builds, uploads
# open http://localhost:8080/console/ and sign in with KARIGAR_OWNER_TOKEN
```
Deploying to Render and importing into Nonilion: [docs/nonilion-setup.md](docs/nonilion-setup.md), [docs/testing.md](docs/testing.md).

**LLM (optional)**: AgentRouter through the official `claude` CLI (`.env`: `AGENTROUTER_API_KEY`). It only shapes briefs and design ideas, always with a deterministic fallback.

## Architecture

```
Nonilion room ──HTTPS──▶ Render: karigar.service (stdlib)  ◀──polls HTTPS── Laptop worker (WSL)
 Sakhi /sakhi/v1          queue · conversations · files ·                   Orchestrator: Sakhi → Jauhari →
 Karigar /karigar/v1      replies written by code · /console              Naqqash → Karigar → Chitrakar
                                                                           bpy geometry · mesh checks · Cycles
```
Replies stream progress lines and return within Nonilion's timeout. Long work keeps running on the worker, and the next message fetches it. Numbers and quotes are sent before renders. If the worker is down, the service answers in about 5 s.

## Layout

```
karigar/core/            domain-free engine: orchestrator, solver, gold maths, calibration, order store, LLM gateway
karigar/packs/jewellery/ brief (Sakhi), pricing + rates (Jauhari), designer (Naqqash), geometry + families/ (19 designs),
                         meshdfm (mesh checks), edits, render, job card
karigar/service/         Render service (stdlib) + worker
console/                 owner web console (static; data from /api)
probe/                   Phase 6.5 Nonilion probe
sim/                     1,000-user simulation (docs/user-sim-report.md)
nonilion/                agent instruction texts
data/                    casting.json, dfm_rules.json, rate_card.json, ring_sizes.json (sourced, labelled "assumed")
docs/                    STATUS, implementation plan, decisions, flow, testing, security
```

## Tests

`wsl -e bash -lc "cd /mnt/c/projects/karigar && ./venv/bin/python -m pytest -q"` runs about 1,100 tests (about 15 minutes, mostly bpy). Tests never call a real model and never write `data/` or `out/`.

Every sourced number (densities, casting minimums, GST, hallmarking, shrinkage) is cited in [docs/decisions.md](docs/decisions.md) "Shop numbers".
